📋 Permission Sets & Permission Set Groups
Permission Sets
A permission set gives users access to fields, classes, objects, flows, etc. If any of those things no longer exist in the org, Salesforce throws an error. CleanZ removes the matching block for that missing item.
1
Missing Custom Field
Salesforce Error
no CustomField named Opportunity.Budget__c found
→
Block Removed from XML
<fieldPermissions> <editable>true</editable> <field>Opportunity.Budget__c</field> <readable>true</readable> </fieldPermissions>
CleanZ extracts Opportunity.Budget__c from the error, then finds the <fieldPermissions> block where <field> matches exactly.
2
Missing Apex Class
Salesforce Error
no ApexClass named MyOldClass found
→
Block Removed from XML
<classAccesses> <apexClass>MyOldClass</apexClass> <enabled>true</enabled> </classAccesses>
3
Missing Apex Page (Visualforce)
Salesforce Error
no ApexPage named MyOldPage found
→
Block Removed from XML
<pageAccesses> <apexPage>MyOldPage</apexPage> <enabled>true</enabled> </pageAccesses>
4
Missing Custom Tab
Salesforce Error
no CustomTab named MyObject__c found
→
Block Removed from XML
<tabVisibilities> <tab>MyObject__c</tab> <visibility>DefaultOn</visibility> </tabVisibilities>
5
Missing Custom Object
Salesforce Error
no CustomObject named OldObject__c found
→
Block Removed from XML
<objectPermissions> <object>OldObject__c</object> <allowRead>true</allowRead> <allowCreate>true</allowCreate> ... </objectPermissions>
6

👤 Profiles
Profiles (ADD Operation)
Profiles are very different from permission sets. Copado's TRIM process strips most sections from a profile before deploying, so Salesforce never sees them and never throws errors for them. CleanZ only handles the three things Copado actually enforces for an ADD profile.
Why not all 13 like permission sets?
Copado TRIM removes fields, classes, objects, pages, tabs, record types, layouts, apps, custom permissions, and custom metadata from profiles before deployment. Those sections are gone before Salesforce even looks — so no errors ever fire for them. CleanZ only needs to handle what actually reaches Salesforce.
1
Missing Flow
Salesforce Error
no Flow named My_Old_Flow found
→
Block Removed from XML
<flowAccesses> <enabled>true</enabled> <flow>My_Old_Flow</flow> </flowAccesses>
2
Unknown User Permission
Salesforce Error
Unknown user permission: ViewAllData
→
Block Removed from XML
<userPermissions> <enabled>true</enabled> <name>ViewAllData</name> </userPermissions>
3
Missing Lightning Page (FlexiPage) in profileActionOverrides
Salesforce Error
The OldDashboard Lightning page doesn't exist or isn't valid — OR — no FlexiPage named OldDashboard found
→
Block Removed from XML
<profileActionOverrides> <actionName>View</actionName> <content>OldDashboard</content> <formFactor>Large</formFactor> <pageOrSobjectType>Account</pageOrSobjectType> <type>Flexipage</type> </profileActionOverrides>
4
profileActionOverrides — Missing Object or Record Type (Pre-check)
This is a pre-deploy check — CleanZ scans the profile XML before deployment and removes profileActionOverrides blocks that point to objects or record types that don't exist in the org, without waiting for an error.
What CleanZ Checks Before Deploy
Each <profileActionOverrides> block's <pageOrSobjectType> and <recordType> values are checked against the org. If the object or record type is missing → the whole block is removed.
→
Block Removed from XML
<profileActionOverrides> <actionName>View</actionName> <content>SomePage</content> <pageOrSobjectType>DeletedObj__c</pageOrSobjectType> <recordType>DeletedObj__c.Old_RT</recordType> <type>Flexipage</type> </profileActionOverrides>
What CleanZ Does NOT Clean for Profiles (Copado TRIM handles these)
fieldPermissions → Copado strips before deploy, no error fires classAccesses → same pageAccesses → same tabVisibilities → same objectPermissions → same (for custom __c objects) recordTypeVisibilities → same layoutAssignments → same applicationVisibilities → same customPermissions → same customMetadataTypeAccesses → same
📊 Report Types
Report Types
A report type defines which fields and relationships can appear in a report. CleanZ handles two kinds of error: a missing field (removes the <columns> block) and a missing relationship (removes the entire <join> block and all column entries that used it). For missing fields, CleanZ tries three routes in order.
How a <columns> block looks in XML
<columns> <field>Budget__c</field> ← field name (bare, no object prefix) <table>Opportunity</table> ← which object this field belongs to <checkedByDefault/> </columns>
1
Standard Route — Field + Object Both Found
Primary Route Used in the vast majority of cases
Salesforce Error
no CustomField named Opportunity.Budget__c found
→
CleanZ Splits the Name
Object → Opportunity Field → Budget__c
→
Block Removed
<columns> <field>Budget__c</field> <table>Opportunity</table> </columns>
How CleanZ Matches the <table> Value
The <table> value is not always a plain object name. CleanZ looks at only the last segment of the path. Examples: Opportunity → last segment: Opportunity ✓ matches Accounts.Opportunities → last segment: Opportunities ✓ matches (plural) User.Opportunity$CreatedById → last segment: Opportunity$CreatedById ✓ contains "opportunity" Opportunities__r → strip __r → Opportunities ✓ matches (plural) For y → ies plural (opportunity → opportunities): "opportunities" does NOT contain "opportunity" as a substring. CleanZ also checks the stem: "opportunitie" IS inside "opportunities". ✓
2
Traversal Fallback — Field is in Lookup Form in XML
Fallback Route Used when standard route finds nothing
Sometimes the SF error says Opportunity.ISR_Owner__c but the XML stores the field as SBQQSC__RenewalOpportunity__c.ISR_Owner__c (a lookup relationship prefix). Standard matching finds no <field>ISR_Owner__c</field> because the tag has the full lookup path. The fallback handles this.
Salesforce Error
no CustomField named Opportunity.ISR_Owner__c found
→
What XML Actually Has
<columns> <field>SBQQSC__RenewalOpportunity__c .ISR_Owner__c</field> <table>Opportunity</table> </columns>
→
Block Removed (fallback)
<columns> <field>SBQQSC__RenewalOpportunity__c .ISR_Owner__c</field> <table>Opportunity</table> </columns>
Fallback Decision Logic
Standard route found nothing. Bare field name absent from XML → fallback activates. Count all <columns> blocks where <field> ENDS WITH "ISR_Owner__c": Count = 1 → Remove it. It must be the broken one. ✓ Count ≥ 2 → Skip. Can't tell which object it belongs to. ⚠ manual fix needed
⚠
Guard — When the Fallback Does NOT Fire
Safety Guard
If the bare field name IS found in the XML but the object doesn't match, CleanZ already made a decision in the standard route — it kept the block because the object was different. The fallback respects that decision and does not run.
Error
Opportunity.ISR_Owner__c
→
XML Has (Different Object)
<columns> <field>ISR_Owner__c</field> <table>Contact</table> ← Contact, not Opportunity </columns>
Standard route: field found but table is Contact → keep it. Fallback: bare field IS present → fallback does not run. Result: nothing removed. Manual fix required.
3
Missing Relationship — Entire Join Block Removed
Salesforce Error
No such relationship OldRelationship__r on object Account
→
Everything for that relationship removed
<join> <outerJoin>true</outerJoin> <relationship>OldRelationship__r</relationship> </join> <sections> <columns> <field>Name</field> <table>Account.OldRelationship__r</table> </columns> ... </sections>
CleanZ removes the <join> block AND every <columns> entry whose <table> path contains the relationship name. If a <sections> block becomes completely empty after column removal, it is pruned too. A stack-based parser handles nested <join> structures safely — only the matching join is removed, outer joins stay intact.
🗂 Layouts
Layouts
Layouts define which fields, buttons, actions, and related lists appear on a record page. CleanZ handles six distinct layout error patterns, all discovered from live Salesforce Metadata API responses. Each has a safety check: if the missing item is part of the current promotion as an ADD operation, CleanZ skips it.
Key XML sections in a Layout file
<Layout> <customButtons>SendEmail</customButtons> ← custom button name (bare, no object prefix) <layoutSections> ← page section <layoutColumns> <layoutItems> <field>Budget__c</field> ← field in the section </layoutItems> </layoutColumns> </layoutSections> <quickActionList> ← quick action bar <quickActionListItems> <quickActionName>Account.NewContact</quickActionName> </quickActionListItems> </quickActionList> <platformActionList> ← platform action panel <platformActionListItems> <actionName>Account.NewContact</actionName> <actionType>QuickAction</actionType> </platformActionListItems> </platformActionList> <relatedLists> ← related list panel <fields>FULL_NAME</fields> ← column shown in the list <fields>CONTACT.EMAIL</fields> <relatedList>RelatedContactList</relatedList> ← which related list (standard) </relatedLists> <relatedLists> ← custom-object related list <fields>NAME</fields> <relatedList>OldObj__c.LookupField__c</relatedList> ← object + lookup field </relatedLists> </Layout>
1
Missing Field in a Layout Section
Salesforce Error
In field: field - no CustomField named Account.Old_Field__c found
→
Block Removed from XML
<layoutItems> <behavior>Edit</behavior> <field>Old_Field__c</field> </layoutItems>
The object prefix (Account.) is stripped — only the bare field name Old_Field__c is matched in the layout XML.
2
Missing Custom Button (WebLink)
Salesforce Error
In field: customButtons - no WebLink named Account.SendEmail found
→
Entry Removed from XML
<customButtons>SendEmail</customButtons>
SF includes the object name in the error (Account.SendEmail) but the XML element holds only the bare button name (SendEmail). CleanZ strips the object prefix before matching.
3
Missing Quick Action
Salesforce Error
In field: QuickAction - no QuickAction named Account.OldAction found
→
Both Entries Removed from XML
<quickActionListItems> <quickActionName>Account.OldAction</quickActionName> </quickActionListItems> <platformActionListItems> <actionName>Account.OldAction</actionName> <actionType>QuickAction</actionType> <sortOrder>1</sortOrder> </platformActionListItems>
One SF error covers both places the action can appear. CleanZ removes from <quickActionList> and from <platformActionList> in a single pass so neither reference remains.
4
Invalid Column Field Inside a Related List
Salesforce Error
Invalid field:Old_Field__c in related list:RelatedContactList
→
Entry Removed — Related List Block Kept
<relatedLists> <fields>FULL_NAME</fields> <fields>CONTACT.EMAIL</fields> <fields>Old_Field__c</fields> <relatedList>RelatedContactList</relatedList> </relatedLists>
Only the single bad <fields> line is removed. The related list panel itself and all other column entries stay intact.
5
Missing Related List — Custom Object Lookup No Longer Exists
Salesforce Error
In field: relatedList - no CustomField named OldObj__c.LookupField__c found
→
Whole Block Removed from XML
<relatedLists> <fields>NAME</fields> <relatedList>OldObj__c.LookupField__c</relatedList> </relatedLists>
The value in <relatedList> for a custom-object related list is ObjectName__c.LookupField__c (the lookup field that creates the relationship). When that field no longer exists, SF reports it as "no CustomField named …". CleanZ removes the entire <relatedLists> block — not just a column field.
6
Related List Name Not Recognised
Salesforce Error
Cannot find related list: RelatedOpportunityList
→
Whole Block Removed from XML
<relatedLists> <fields>NAME</fields> <fields>AMOUNT</fields> <relatedList>RelatedOpportunityList</relatedList> </relatedLists>
Standard related lists use names like RelatedContactList, RelatedCaseList, RelatedOpportunityList. If the name is wrong or the feature is disabled in the target org, SF returns this error. The entire block is removed.

4 Invalid field:X in related list:Y The single <fields> line inside the related list Single column entry
