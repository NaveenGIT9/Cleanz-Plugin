Salesforce DevOps Utility

CleanZ

An intelligent Salesforce metadata cleaner that is error-driven — reads every deployment failure from the org, automatically resolves invalid references in Permission Sets, Profiles, and PSGs, and loops until clean — before they break your Copado promotion.

The Problem
Why CleanZ Exists

When metadata is promoted between Salesforce orgs, references to missing components (fields, classes, packages) cause deployment failures. Manually hunting each error is slow and error-prone. CleanZ automates the entire fix loop.

Real-World Scenario — Org Drift

✗ … × 20 errors — deployment blocked

When Is CleanZ Useful?
✓Fields / objects deleted from destination org after the feature branch was created
✓Managed package (CPQ, OmniStudio, etc.) installed in DEV but not in QA/UAT
✓Apex classes / pages removed from the org but still referenced in a PS/Profile
✓PS/Profile accumulated stale refs over many merges — one run cleans everything
✓User license differences between orgs causing permission flag rejections
✓Duplicate XML blocks from Copado auto-merging the same component from two stories
Inputs
What You Provide to Run CleanZ
1 — Promotion Changes JSON

The Copado promotion package JSON serves two purposes for CleanZ:

①Source of work — CleanZ reads this to identify which PermSets, Profiles, and PSGs are part of this promotion and need to be cleaned.
②Whitelist — any component listed in this JSON is protected. CleanZ will never remove a ref to something that's being deployed in the same promotion.
2 — Target Org Alias

The SFDX alias of the destination org (e.g. rbkpipeqa). CleanZ authenticates against this org to run dry-run validations and query installed packages and org components.

⚠
Cascade Removal for Missing Objects

When a custom object is missing, CleanZ removes not just the <objectPermissions> block but also every <fieldPermissions> entry for that object's fields AND every <layoutAssignments> block referencing that object — all in one pass.

ℹ
Layout Pre-Run Fixes (before first deploy)

Duplicate fields (Field: field, value:X appears more than once) and malformed XML tags (Element layoutItems duplicated) in Layout files are fixed in a pre-run pass before the first deploy attempt — committed separately so the fix history is clean.

Category 2
Namespace Bulk Removal

When any error references a managed package component (e.g. SBQQ__Field__c), CleanZ checks if that package's namespace is installed in the target org. If not — it bulk-removes every reference to that namespace across ALL block types in one pass.

📦
Example — CPQ (SBQQ) not installed in target org

One error on any SBQQ__ component triggers a single bulk pass — every reference to that namespace across all block types in PermSet, Profile, PSG, Layout, and ReportType files is removed at once. CleanZ queries InstalledSubscriberPackage once per run to confirm the package is missing before acting.

Category 3
User License Errors — Surgical Fix

Two distinct user-license errors — handled differently depending on what Salesforce actually reports.

🗑

Unknown User Permission

The permission name doesn't exist at all in the org's license edition.

Unknown user permission: ManageDataCategories

→ Entire <userPermissions> block is removed.

✂

License Doesn't Allow Flag

Object is valid but a specific boolean flag exceeds the license tier.

The user license doesn't allow the permission: View All Account

→ Only <viewAllRecords>true</viewAllRecords> removed. Rest of objectPermissions block stays intact.

Category 4
Manual Fix Errors — Dynamic Masking

Some errors cannot be safely auto-fixed — removing the block blindly could break org behavior. CleanZ temporarily masks these blocks during the dry-run loop so other errors in the same file can still be discovered and fixed. After the run, they are flagged clearly for manual resolution.

🎭
What "Masking" Means

The block is stripped from the XML only for the dry-run validation — it is not committed to the branch. CleanZ re-validates without the masked block to surface all remaining errors. After the run, the original file is preserved and the error is listed in the Conclusion report as "Needs Manual Fix."

🌐

IP Login Ranges

Org has IP range limits (IPv4/IPv6 count exceeded).

Error: ip range / ipv4 limit exceeded

Mask: <loginIpRanges> block temporarily hidden.

Why manual: IP ranges are an org-level security setting — requires deliberate configuration, not blind removal.

Efficiency Feature
Cross-Sweep & Repo-Wide Sweep

When a missing ref is found in one file, the same removal is immediately applied to all other files in the current batch — and then swept across the entire repo at the end.

⚡ Cross-Sweep (Same Run)

When Account.Score__c is found missing in PermSet_A, CleanZ immediately removes it from every other PermSet and Profile in the same promotion batch — without waiting for them to individually fail the dry-run. The same applies to ReportType columns: a field error on one ReportType triggers an immediate cross-sweep across all other ReportTypes in the batch.

Structural Fix
Exact Duplicate Block Removal

Salesforce rejects files that contain duplicate XML blocks (e.g. the same field permission appearing twice). CleanZ detects and deduplicates these before the first dry-run.

🔎

What Gets Deduplicated

All major block types are checked for exact duplicates: fieldPermissions, classAccesses, objectPermissions, tabSettings, flowAccesses, recordTypeVisibilities, customMetadataTypeAccesses, customPermissions, categoryGroupVisibilities.

✓

Common Cause

Merge conflicts resolved by keeping both sides, or Copado auto-merging the same component from two different stories into the same file. CleanZ catches these silently before they cause a deployment failure.

Special Handling
Permission Set Groups (PSG)

PSGs have unique behavior in Salesforce — after every deploy they enter a background recalculation state. CleanZ handles this specifically.

Step 1 — Fix Structure

Before deploying, CleanZ checks that <permissionSets> entries are:

✓ No duplicates ✓ Positioned after <label> ✓ Alphabetically sorted

Salesforce throws "Element permissionSets is duplicated at this location" if these rules are violated.

Step 2 — Deploy & Poll

After each PSG dry-run, CleanZ polls the org for recalculation status:

Updated → ✅ Continue CalculationFailed → 🔁 Retry (transient) Other → ⛔ Manual intervention

Polls every 30s, waits up to 10 minutes for recalculation to complete before proceeding.

Step 3 — Verify PS Members Against Target Org

Every PermissionSet listed inside the PSG is verified against the target org. Any PS that doesn't exist in the org and isn't in the promotion JSON is removed from the PSG before deploying.

Salesforce rejects a PSG if it references a PS that doesn't exist in the org.

Key Design Decision
Mimicking Copado Deployment Behavior

Standard Salesforce validation and Copado promotions behave very differently. CleanZ is built to match Copado's actual behavior — not SF's default — so the dry-run results accurately predict whether the real Copado promotion will succeed.

1
ADD vs FULL Mode

Copado ADD promotions only enforce a subset of profile sections (flowAccesses, userPermissions, profileActionOverrides). CleanZ detects ADD vs FULL from the promotion JSON operation field and masks the irrelevant sections — exactly as Copado TRIM does — to avoid false positive failures.

2
TRIM Masking

Copado TRIM strips many sections before deployment (categoryGroupVisibilities, classAccesses, pageAccesses, applicationVisibilities, etc. in profiles). CleanZ pre-masks these same sections so its dry-run doesn't fail on things Copado would silently strip anyway.

3
Deploy Queue Awareness

Before each dry-run, CleanZ checks the org's deploy queue via Tooling API. If a Copado promotion is already running, it waits for the queue to clear before submitting — preventing validation jobs from piling up and timing out.

4
Transient Error Retry

Network drops, rate limits, session expiries, ECONNRESET — CleanZ retries with exponential backoff up to 10 times before giving up. The run doesn't fail just because the VDI had a blip mid-validation.

🎯
The Goal

If CleanZ says the promotion is clean — it is clean for Copado. Standard SF validation would give you false positives (stripping things Copado never deploys) or false negatives (skipping Copado-specific checks). CleanZ bridges that gap so Salesforce teams using Copado can trust the result.
